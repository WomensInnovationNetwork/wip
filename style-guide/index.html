Maintainers only — not a member page

This is the working reference for anyone editing Women in Power pages. It is deliberately not linked from any member-facing page and is excluded from search engines. Mentors and mentees should never be sent here — if you are adding navigation to a member page, do not add a link back to this one.

01

Foundations

Who we are

Women in Power (WiP) is the largest grassroots organisation of women working with, and in, the Microsoft Power Platform ecosystem. We focus on mentorship, skilling, and bringing women together to build relationships and help each other grow.

Women in Power is a programme of the Women’s Innovation Network (WIN), a non-profit built to get more women into the room, growing, learning and connecting.

When women innovate, the future follows

The public-facing line. Use it as a closing note or a masthead kicker — not as a headline on every page.

Together we WIN

The internal rallying line, and the reason for the acronym. Use inside member and volunteer pages, sparingly.

Lead. Create. Empower.

The skilling-series line. Reach for it on learning and events content, not on mentoring pages.

What every page has to do

  1. Answer “what did I sign up for?” above the fold. The single loudest piece of cohort feedback was that people did not know what they had joined. Dates, format and time commitment go near the top, always.
  2. Be readable on a phone, at 6am, before coffee. Most members open these between meetings.
  3. Print cleanly. People print the calendar and stick it on a wall. The stylesheet handles this — do not fight it.
  4. Never publish anything internal. Committee staffing, participant counts, gaps, unconfirmed decisions and anything said in a leadership channel stay off member pages.

02

Information architecture

Three pillars at the top level. Everything else lives inside one of them. Nothing sits at the root except the overview.

/ Women in Power — overview ├── /mentoring/ pillar 1 │ ├── 2026-cohort2/ │ └── mentorship-prompts/ ├── /skilling/ pillar 2 — not built yet └── /networking/ pillar 3 — not built yet

Two levels of navigation

Primary — the masthead

Only ever the three pillars: Mentoring, Skilling, Networking. Identical on every page. It does not grow when a pillar gains a page.

Secondary — the sub-nav

Appears on pages inside a pillar, listing that pillar’s pages. Labelled with the pillar name so a reader always knows which section they are in.

Rules

  • A new page belongs to a pillar. If it does not fit under Mentoring, Skilling or Networking, that is a sign it needs its own pillar — or that it should not be a page.
  • The primary nav stays three items. Cohort 2 and the Prompt Pack are Mentoring pages, so they belong in the sub-nav, not the masthead. That is what keeps the top level readable as Skilling and Networking arrive.
  • Pillars without pages say so. A .nav-soon span, not a link. A nav item that 404s is worse than one that admits it is not ready.
  • The logo goes home — to the overview, never to a section page.
  • The sub-nav is never sticky. The cohort page already has a sticky in-page jump bar; two stacked sticky strips eat a phone screen.

Adding the Skilling pillar

  1. Create skilling/index.html from any existing page as a starting point.
  2. In every page’s masthead, swap <span class="nav-soon">Skilling <em>soon</em></span> for a real link at the right relative depth.
  3. If Skilling gains a second page, add a sub-nav to it with subnav-label set to “Skilling”.
  4. Update the pillar card on the overview page, and the table in the README.

03

Voice and tone

Warm, direct, a little bit fired up. We are peers talking to peers — not an HR portal, and not a hype account.

Do

Say the thing. “Six sessions, one hour each, every other Tuesday. About an hour a week.”

Use second person. “You’ll pick a breakout room by topic.”

Be honest about effort. Publish real hours. People plan around them.

Don’t

Over-explain or over-apologise. No “we’re so sorry to ask,” no “just a quick note.” Same warmth, half the words.

Stack emoji. Great on LinkedIn, noisy on a reference page. One per section at most, and only where it aids scanning.

Use corporate filler. No “leverage,” “synergies,” “journey of transformation.”

04

Logos

Two marks, one hierarchy. Women in Power leads on programme pages; WIN signs off in the footer as the parent organisation.

WIN — primary mark

Navy wordmark, gradient ribbon above, tagline beneath. Use on a light ground. Clear space on all sides = the height of the W in WIN.

Women in Power — wordmark

Black text lockup only — the silhouette is not used in page furniture. Use the reversed file on dark grounds; every masthead carries that one.

Still raster, not vector

Both wordmark files are PNGs rebuilt from a supplied JPEG — the background was keyed out and a white variant generated. They are sharp at the sizes used here, but the script lettering will soften if scaled much larger. Replace with an SVG master when one turns up.

Rules

  • Never re-colour, stretch, rotate or add a drop shadow to either mark.
  • The gradient ribbon runs cyan → violet → magenta, left to right, in that order. Never reverse it.
  • On dark grounds use the reversed (white) wordmark. Do not place the navy mark on navy.
  • Minimum size for the WIN mark: 120px wide, so the tagline stays legible.

The one colour rule that matters

The ribbon gradient is for accent only: rules, badges, numerals, short headline fragments, icon plates. Never set body copy in gradient text, and never run it behind a paragraph. If a page starts to look like a nightclub flyer, cut the gradient back to a 3px rule and the energy returns.

06

Light and dark

Every page ships in both. Readers get whatever their device asks for, and can override it from the toggle in the masthead.

Auto

The default. Follows the operating system’s light/dark setting, and switches live if the reader changes it.

Light

Forced light, whatever the system says. Stored per browser.

Dark

Forced dark. The choice survives a reload and applies across all WiP pages on that browser.

The rule that keeps this working

Every colour gets its base value on bare :root. Dark mode only redefines tokens, in two places — a prefers-color-scheme block guarded against an explicit light choice, and a [data-theme="dark"] block so the toggle wins in both directions.

:root { --surface: #ffffff; } /* base - always defined here */ @media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { --surface: #121c31; } } :root[data-theme="dark"] { --surface: #121c31; }

Never give a colour its only definition inside a media query — the toggle cannot reach it, and the page breaks in one of the three states.

Two things to remember when you add a page

  1. Put the pre-paint snippet in <head>, before the stylesheet. It reads the stored choice and stamps data-theme before first paint, so there is no white flash on a dark-mode load.
  2. Give the masthead a <button class="theme-toggle" data-theme-toggle> and load wip.js. The script fills in the icon and label and wires up the cycle.

Storage is wrapped in try/catch: in a private window, or with site data blocked, the toggle still works for the session and the page falls back to the system preference.

Type

Poppins for display — it matches the geometry of the WIN wordmark. Inter for body. Both fall back to Segoe UI and the system stack, so a page still reads correctly if webfonts fail.

  • Headings are display weight 700–800, tight tracking (-0.015em), navy. Never gradient except for a deliberate one- or two-word accent.
  • Body copy caps at 72ch. Long measures are the fastest way to make a page feel like homework.
  • Line height 1.62 for body, 1.2 for headings.
  • Only one h1 per page, and it says what the page is.

FAQ

Can I do both tiers at once?

No — you are placed in one tier for the cohort. Tier 1 graduates move into Tier 2 next time round.

What if I miss a session?

Nothing breaks. Certificates have an attendance threshold rather than a perfect-attendance requirement.

Journey explorer

The interactive walkthrough on the cohort page: a reader picks a tier and a role, then steps through the milestones. Live example: Cohort 2 → Your journey.

How it is built

  • One copy of the words. The four journeys live as ordinary timeline lists inside .je-source. The widget reads them from the page, so there is no duplicated JavaScript copy to drift out of date.
  • It degrades. With JavaScript off, .je-source is simply visible and all four journeys read as plain timelines. Print does the same, deliberately.
  • It is a real tablist. Step dots are role="tab" owned directly by the role="tablist" rail, with roving tabindex, arrow-key / Home / End navigation, and one focusable panel.
<div class="journey-explorer" data-tier="1" data-role="mentee"> <div class="je-controls"> <!-- two role="radiogroup" segmented controls --> <div class="je-stage"> <div class="je-rail" role="tablist"></div> <!-- built by wip.js --> <div class="je-panel" role="tabpanel" tabindex="0"></div> <div class="je-foot"> <!-- progress bar + prev/next --> </div> <div class="je-source"> <div class="je-journey" data-tier="1" data-role="mentee" data-total="About 11.5 hours..."> <ol class="timeline"> <li data-label="Sign up"> <!-- short label for the rail --> <div class="tl-when">...</div> <div class="tl-title">...</div> <p class="tl-body">...</p> <span class="tl-time">15 min</span> </li> </ol> </div> </div> </div>

To add a journey: drop another .je-journey with its own data-tier and data-role into .je-source, and add the matching option to the segmented control. No JavaScript changes needed.

Back to top

On by default for long pages. It is already on this page — scroll down and it appears at the bottom right.

Why it is built the way it is

  • It is an <a href="#top">, not a <button>. With JavaScript off it still works as an ordinary anchor. JS only decides when it shows and moves focus — neither of which a bare anchor does well.
  • It appears late. Not until roughly one screenful down (max(400px, 90vh)), so it never covers content on a short page or sits there uselessly at the top.
  • 48×48px, comfortably over the 44px minimum touch target, and inset with env(safe-area-inset-*) so it clears the home indicator on phones.
  • It moves focus, not just the viewport. Scrolling alone strands a keyboard or screen-reader user’s focus where they were, so the next Tab drops them back down the page. On activation it focuses #top, adding tabindex="-1" only for the duration so the header never joins the tab order.
  • Reduced motion respected. Smooth scroll becomes an instant jump, and the fade-in loses its transform.
  • Cheap. A passive scroll listener coalesced with requestAnimationFrame, so at most one check runs per frame.
  • Hidden in print.
<header class="masthead" id="top"> <!-- the landing target --> <a class="to-top" href="#top" title="Back to top"> <span class="visually-hidden">Back to top</span> <svg ...></svg> <!-- aria-hidden, the label above names it --> </a>

Place the anchor just before the wip.js script tag, and put id="top" on the masthead. Nothing else is needed — wip.js picks it up.

Accessibility

Non-negotiable. A member page nobody can read is a page that failed.

  • Contrast. Body ink on the page ground clears WCAG AA comfortably. The bright ribbon colours are decoration — never put small text in cyan or magenta on white.
  • Never colour alone. Tier colours always carry a text label too (“Tier 1 · Group”), because roughly one in twelve readers will not see the hue difference.
  • Focus is visible. A 3px violet ring, defined once globally. Do not remove outlines.
  • Real semantics. One h1, headings in order, <table> for tabular data, <details> for FAQs. Every page opens with a skip link.
  • Reduced motion respected. Transitions and smooth scroll switch off automatically.
  • Alt text. Logos get their organisation name. Decorative gradients get aria-hidden.
  • Zoom. Everything is rem-based and reflows to 320px. Test at 200% before merging.

How to evolve this

This guide is meant to change. Here is how to change it without it falling apart.

  1. Change the token, not the page. All colour, type, space and radius live in :root in wip.css. If you find yourself writing a hex value in a page, add a token instead.
  2. Page-specific CSS stays in that page’s <style> block. Only promote it into wip.css once a second page needs it.
  3. Add the component here when you add it there. A component that is not on this page will get reinvented by the next person.
  4. Bump the version in the masthead and note what changed in the log below.
  5. Ship it as a pull request so the committee can see the change before it goes live.
